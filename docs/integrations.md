# Sonarr, Radarr, and webhooks

Configure optional Sonarr/Radarr base URLs (HTTP or HTTPS, including any reverse-proxy path prefix) and API keys under Settings. Tests use `/api/v3/system/status` and only read saved settings. Keys are encrypted under `/config` and never returned by the settings API. HTTP uses the trusted LAN; HTTPS is preferable across untrusted networks. Loopback, link-local, metadata-service addresses, redirects, credentials in URLs, and prohibited DNS results are rejected. Private LAN addresses remain supported. Each DNS answer is checked and the chosen address is pinned for the request; requests time out after eight seconds.

Library audits use Sonarr series/episode/episode-file joins and Radarr movie/movie-file resources. Missing or inconsistent identity cannot authorize remediation. Multiple-episode files and ambiguous release/pack history require manual attention in either remediation mode.

## Import notifications

In Media Guard Settings, expand the integration's webhook configuration and Generate / rotate token. Copy the shown token; only its hash is stored and rotation immediately invalidates the previous token. In Arr Settings → Connect, add a Webhook with POST, On Import / On Upgrade, URL `APP_URL/api/webhooks/sonarr` or `APP_URL/api/webhooks/radarr`, and advanced header `Authorization: Bearer TOKEN`. Arr's Test notification is supported. Use the URL reachable from Arr, with HTTPS on untrusted networks.

The native receiver uses per-integration bearer tokens, not `WEBHOOK_SECRET` or an HMAC header. Authenticated Download events commit a replay receipt and durable scan job in one transaction. Duplicate import identities do not enqueue a second job. Body size is bounded to 256 KiB. File paths must pass configured mappings and media-root validation before inspection. Do not publish tokens in URLs or logs.

## Guarded replacement contract

Manual Fix & Redownload permits one explicitly selected item at a time. Audits, schedules, webhooks, Rescan, and Rescan displayed media only inspect files in this mode; they never quarantine, blocklist, or search. An immediate database transaction refuses another remediation while a job is queued/running or a replacement is pending. Uncertain operations also block admission until inspected. Only a proven pre-mutation failure can use the explicit retry action. Monitor Only remains the default; both remediation modes require `ALLOW_DESTRUCTIVE_ACTIONS=true`.

Automatic mode is separate: scans can remediate every eligible failure. Both modes are validated against isolated contract fixtures, not live services. It requires unambiguous current file identity, a failed persisted scan, and matching imported/grabbed history. Disable Arr's automatic failed-download redownload so Media Guard owns the search budget. The workflow quarantines the failed file, requests RescanSeries/RescanMovie, waits for reconciliation and checks the original file is absent, marks the identified grabbed history failed through `/api/v3/history/failed/{id}`, corroborates a new matching blocklist entry, then issues EpisodeSearch/MoviesSearch once. This uses Arr's supported failed-history rejection/blocklisting path; Media Guard does not invent a direct blocklist insertion API or delete a possibly replaced file through Arr.

Every uncertain external outcome stops in Needs Attention. A later import notification or audit verifies a replacement only with a different Arr file ID, current mapping/identity, and fresh persisted passing evidence. A search being accepted is not a verified replacement. If an Arr version rejects these API contracts, retain the quarantined file and inspect the operation rather than replaying mutations.

### History and blocklist evidence

The lookup follows the reviewed Sonarr 4.0.20.3014 and Radarr 6.4.4.10685 contracts. It first reads `/api/v3/history?episodeId=...` for Sonarr or `/api/v3/history?movieIds=...` for Radarr. Import correlation requires exactly one usable `data.importedPath` matching the current Arr library path directly or through at most 16 exact Arr-recorded rename transitions after conservative POSIX normalization. Sonarr `episodeFileRenamed` and Radarr `movieFileRenamed` use `data.sourcePath` → `data.path`. The reverse chain must have the same episode/movie identity, no forks, multiple predecessors, cycles, or missing required paths, and no rename away from the current terminal path. Unrelated rename history is ignored. Control characters, backslashes, traversal and uncertain identities are refused. `droppedPath` is the download/import source and never a fallback for library matching.

Next, `/api/v3/history?downloadId=...` retrieves download-wide evidence without a title filter, preserving visibility of shared downloads. Missing IDs, incomplete imports, conflicting release metadata, or foreign episode/movie events refuse remediation. Identical repeated grabbed evidence is allowed; multiple imports reaching the current path are refused, even if they share a download ID. Each history or blocklist lookup has a maximum of ten 100-record pages; duplicate IDs, changing totals, incomplete pages, or exceeded bounds fail closed.

Before mutation, the pipeline snapshots `/api/v3/blocklist?seriesIds=...` or `?movieIds=...`. After marking the exact grabbed history record failed, it requires exactly one new matching entry with the same source title, indexer, protocol, quality, movie/series identity, and exact single-episode identity where applicable. A successful POST alone, an old entry, or an absent/ambiguous match never authorizes search. These Arr blocklist resources do not expose download IDs or hashes: this check corroborates the release using exposed fields, but cannot independently prove hash identity or rule out an indistinguishable concurrent external action. Arr's own failed-download redownload must remain disabled; Media Guard does not change that setting.

The operation journal records `mutation-started`, then `quarantine-intent`, `rescan-command-intent`, `history-failed-intent`, and `replacement-search-intent` before each corresponding dispatch. Outcomes are recorded separately; `blocklist-verified` precedes search intent. An unknown outcome cannot be blindly replayed. Completion requires fresh passing replacement evidence; the failed copy remains quarantined. Explicit cleanup records `cleanup-intent` before unlink and `cleanup-complete` afterward, and revalidates both replacement evidence and the retained copy.

The exact legacy v0.2.6 refusal `Disable Arr automatic failed-download redownload before using Automatic mode` can be classified as pre-mutation only with needs-attention state, null release/quarantine IDs, no mutation or unknown steps, and no quarantine, retry reservation, or competing-operation evidence. This read-only classification neither deletes nor resets an operation. Explicit retry revalidates current persisted failure, fingerprint, identity, and safety gates; any possible mutation remains blocking.
