# Planned v0.2.2 stabilization report

This records the initial stabilization at `166a3bb`. See the [wizard/branding persistence follow-up](wizard-persistence-follow-up.md) for the subsequent findings, fixes and expanded verification.

This is unreleased main-branch work. Package/Docker versions remain 0.2.1 until release approval. No v0.2.2 tag, GitHub Release or GHCR publication was created. No production containers, live media, Unraid, Sonarr, Radarr, Plex, Jellyfin or H&H Streaming were accessed or modified.

## Findings and implementation

1. **Config root cause:** v0.2.1 runs as 100:101, which cannot write a fresh Unraid nobody:users (99:100), mode-755 bind mount. Reproduced with the immutable 0.2.1 image, a valid key/origin and an isolated fresh directory: startup exited 1 with the old generic error.
2. **Ownership solution:** a short root entrypoint validates boundaries, opens a fixed allowlist through pinned directory file descriptors and changes ownership only for `/config`, SQLite database/WAL/SHM, and flat branding entries. There is no recursive chown or chmod, no data reset, and no media traversal.
3. **Unraid suitability:** it handles both fresh bind mounts and existing application-owned data, while selecting a conventional host-compatible identity. The host appdata path remains user-selectable.
4. **PUID/PGID:** implemented and validated as non-zero decimal integers up to 2147483647; invalid values fail closed without echoing supplied input.
5. **Defaults:** new Unraid template 99:100; image/Compose without explicit values 100:101 for existing installations. Explicit Docker `--user` skips repair, requires writable appdata and must match any supplied PUID/PGID.
6. **Non-root runtime:** entrypoint execs `su-exec`, drops supplementary groups/UID/GID and execs Node as PID 1. Production tests check the actual PID 1 executable, UID/GID and zero effective capabilities. Image `USER root` is for initialization; Docker exec defaults accordingly, so maintenance should specify `--user` when appropriate.
7. **Media boundaries:** fixed `/Media`, `/movies`, `/tv` and configured roots are checked for canonical-path and mount-backing overlap. Nested config mounts are rejected. O_NOFOLLOW, regular-file validation and single-link checks reject symlink/hardlink escapes before ownership writes. Tests cover these attacks and compare media owner/group/mode after all lifecycle steps. Media remains a read-only mount and writes fail. This assumes an honest host/Docker administrator and a dedicated appdata mount; no container can protect against a privileged host changing its mounts maliciously.
8. **Startup diagnostics:** `startup.failed` codes distinguish missing/malformed/wrong-length encryption keys, invalid APP_URL/ALLOWED_ORIGINS, missing/unreadable/unwritable config, database open/migration failure, runtime conflict and unknown initialization failure. Fields include CONFIG_PATH/EXISTS/READABLE/WRITABLE and runtime UID/GID. Bootstrap has its own safe errors. No raw exception stack or secret is emitted.
9. **Sonarr root cause:** the shared UI disabled Test Connection until an API key was already saved; its POST contained no form data. The server read only saved URL/ciphertext. Thus unsaved first-run tests were impossible and edited values were ignored. The blanket catch hid the real failure class.
10. **Sonarr fix:** enable testing with current input, POST URL/key, use current plaintext transiently or decrypt the saved key when blank, call API v3 status with X-Api-Key, and require Sonarr identity and a supported numeric version response. Save remains a separate encrypted operation.
11. **Radarr root cause:** the same shared UI/POST/saved-only implementation; not a separate Radarr transport implementation.
12. **Radarr fix:** the same corrected path, requiring Radarr identity. A Sonarr response cannot satisfy a Radarr test and vice versa.
13. **Shared cause:** yes for the reproduced unsaved/stale-input failure. No evidence showed a separate encryption or LAN-IP prohibition defect. We did not access live services, so cannot attribute every historical saved-credential failure to a particular network/key condition without its diagnostics.
14. **Exact path:** `IntegrationSettings.tsx` → POST `/api/integrations/[id]` → `ArrClient.testConnection` → `arrTransport`. Shared URL joining preserves the optional base path and removes trailing slashes; DNS pinning, SSRF rules, request limits, TLS validation and timeout bounds remain enforced.
15. **Sonarr before save:** production browser enters current URL/key, rejects a bad key, then succeeds with the correct key before Save; GET confirms no credential was persisted by testing.
16. **Sonarr after save:** browser saves, reloads with an empty password input, then tests successfully through saved-key decryption.
17. **Radarr before save:** identical independent proof against the Radarr mock on its own port.
18. **Radarr after save:** identical saved/reloaded proof with Radarr identity validation.
19. **Restart proof:** both connections pass after stop/start and remove/recreate, including changing from template 99:100 to legacy-default 100:101. Restoring the original key after a wrong-key run restores both connections without data replacement.
20. **Encryption audit:** AES-256-GCM format and migrations remain unchanged; plaintext is encrypted once on save and decrypted only server-side for outbound requests. The browser receives only configuration status, never saved plaintext or ciphertext. SQLite checks confirm ciphertext storage. Wrong-key errors are safe and actionable; existing data is not reset/re-encrypted. Known plaintext/key/password values are absent from app logs and error bodies.
21. **Networking docs/UI:** explain localhost, bridge-mode host IP plus mapped ports, shared-network container names, URL bases, trusted HTTPS and error classes. No personal server address is used.
22. **Template:** complete named/described WebUI 3938, appdata rw, user-selected `/Media` ro, required private encryption key and App URL, optional extra origins, Media Roots `/Media`, TZ `Etc/UTC`, destructive false, PUID/PGID, existing names and fixed fox icon. A CI contract checks XML, fields, defaults and absence of personal paths/IP/timezone/key.
23. **First-run UX:** no ordinary appdata chown step; test before saving; useful connection errors; optional extra origins clearly explained. Existing branding customization remains intact and the two fixed icons stay builder-managed.
24. **Auto-generated encryption key:** intentionally not implemented. Keeping key material separate from appdata preserves existing backup/key-separation and recovery assumptions, avoids precedence changes for environment-key installs and eliminates accidental key regeneration. Explicit generation is documented and remains required.
25. **Origin default:** omitting ALLOWED_ORIGINS already safely permits APP_URL only (or the existing local development fallback when APP_URL is absent). Additional explicit origins remain supported. No wildcard/Host-header trust or CSRF weakening was introduced.
26. **Healthcheck:** retained the existing useful unauthenticated, non-mutating local database/ffprobe readiness check: 30s interval, 5s timeout, 10s start period, three retries. New lifecycle tests wait for Docker's actual healthy state and check Monitor Only/destructive false.
27. **Secret handling:** only authored SafeError messages cross startup/connection error boundaries. Raw DNS/socket/TLS errors and upstream bodies are not returned. Status versions are bounded/numeric, wrong-service errors use the expected known service name, and encrypted-key exceptions are translated into a safe recovery message. Auth/CSRF checks still precede testing. Unsaved tests do not rewrite saved test history; saved tests retain sanitized result/error history.

## Verification and delivery

28. **Files changed:** see the inventory below. Runtime, connection UI/API, Docker entrypoint, official template, tests, CI/release gates and documentation are covered. No dependency version, database schema, fixed branding asset or published version was changed.
29. **Tests added:** 42 unit cases for startup/key/origin/config-boundary/identity/URL/error behavior; distinct real HTTP/HTTPS Sonarr/Radarr fixtures; five lifecycle browser phases; production startup rejection and media-boundary checks; official template validation. Existing security, remediation, migration and browser checks remain enabled.
30. **Test count:** 229 unit tests across 22 files, plus six production browser executions (existing workflow and five Unraid lifecycle phases), template contract and shell/container assertions.
31. **Automated results:** typecheck, zero-warning lint and full unit suite pass. New production tests cover valid/invalid keys, 401/403/404, no/trailing slash and URL bases, trusted HTTPS/untrusted TLS, DNS/refused/unreachable/timeout, unexpected/wrong service, current-input and saved tests, secret redaction and wrong-key recovery.
32. **Production build:** Next.js production build passes.
33. **Docker runtime:** production image build, non-root PID 1, zero effective capabilities, safe default health response, real Docker health state, graceful exit and both browser gates pass in isolation.
34. **Security verification:** dependency audit reports zero vulnerabilities; secret scan, retained SSRF/DNS-pinning/TLS/CSRF/auth/migration/remediation tests and ownership-escape regressions pass. Runtime logs never include fixture API keys, encryption key or password. CI/Release YAML passes actionlint; the release consistency gate passes without triggering publication.
35. **Template validation:** `python3 scripts/check-unraid.py` passes and runs in both CI and Release workflows. Compose interpolation validation passes with a test-only key.
36. **Fresh install:** initially empty 99:100 mode-755 bind mount, no DB/settings, read-only generated `/Media`; initialization creates usable persistent state, UI responds, Docker becomes healthy and Monitor Only/destructive false remain defaults.
37. **Restart/recreation:** settings, admin login, both encrypted integrations, scan-history/release/retry markers and custom logo survive stop/start and removal/recreation. Changing selected non-root IDs does not regress permissions. Wrong-key then restored-key tests preserve the same database.
38. **Migration for manual installs:** no mandatory new variable or schema migration. Keep the existing dedicated /config host path and key. Image updates do not add template variables or mounts to manual Unraid containers.
39. **Current working v0.2.1 install:** no setting changes required for its existing 100:101 appdata, valid origins/key and configured media roots. Upgrade only after approval; do not run old/new instances against the same config concurrently. Preserve a config/key backup.
40. **New required settings:** none for existing valid installations. PUID/PGID are optional; new template defaults are 99/100. Existing explicit encryption key and App URL requirements continue; extra origins remain optional.
41. **Proposed v0.2.2 contents:** scoped ownership bootstrap, non-root identity selection, startup diagnostics, shared Sonarr/Radarr Test Connection fixes, credential/error hardening, completed Unraid template/docs and permanent fresh-install/lifecycle/security gates. Version bump, release tag/publication and GHCR alias movement await explicit approval.
42. **Known limits:** live connectivity was not tested; unusual ACLs/root-squashed filesystems and intentionally non-writable config modes require administrator correction and fail clearly rather than chmod broad permissions. Config must be a dedicated mount with no nested mounts/symlinks/hardlinks in managed entries. Private TLS CAs must be trusted explicitly; TLS verification stays enabled. Only the existing supported linux/amd64 publication target is covered. Numeric API status versions are required; unknown formats fail safely. No known blocker remains in the tested supported configuration.
